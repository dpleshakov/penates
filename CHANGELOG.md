## [Unreleased]

### Added
- `t` opens the target list under the header: fuzzy search over the display name and the path, the current target marked beside the counts of its kits and installed items, `+ add target` with directory completion and the existence line, and `ctrl+r` renaming the display name the header shows. `enter` switches targets: the pending actions of each target stay saved with it — switching never asks and never discards — and a target that holds saved pending actions offers them for restoration on entering.
- `ctrl+d` on a target row removes it through the dialog: either its installed items are removed through the summary and the target is forgotten when the apply completes, or the target is forgotten at once — its lock deleted, its files untouched and no longer owned.
- `e` on a kit row points the kit to a new directory through the path input with directory completion: the pane previews the kit the new directory holds, a kit of another name is a rejection — "Add it as a new kit instead" — and an unreadable kit's pane states its read error and the installed items it keeps frozen until the kit points somewhere readable.
- Kits detach from the target with `d` on the kit row: a kit without installed items detaches at once with a notice, one with installed items opens a dialog — remove its items from the target first, and the kit detaches when the apply that removes them completes (its row shows "detaching" until then), or keep them installed as orphans. The apply's results report the deferred detach it completed and the one it dropped with the items that remained.
- Kits and targets are managed as state operations with their invariants: a kit attaches to a registered target and detaches from it at once, or as a deferred operation that waits for the apply removing its installed items in the target — the deferred operation completes only when that apply removed everything it covers, and is dropped with a shown reason otherwise. A kit path is re-pointed only to a directory that holds a kit with the same name. Forgetting a target deletes its lock and never touches the files in it.
- A major version bump is marked for review: the update marker of an item whose new major differs from the installed one renders in the error style, next to the version arrow.
- Selected items with file contributions install from a kit into a harness configuration directory, and a per-target lock records every file that penates writes.
- Starting with a kit path registers the kit and its target directory; without arguments, the registered target opens directly.
- Items with json contributions install their values into shared JSON and JSONC files: each value lands by its RFC 6901 location, comments and formatting of untouched parts survive, an equal value owned by another installed item makes the item a co-owner, and the lock records every owned location with the hash of its value.
- Items with variables ask for the missing required ones in a form before planning: answers are stored in the lock and reused on the next run, templated contributions get `{{var}}` substituted, and an unknown placeholder or a required variable without a value excludes the item.
- Installed items are updated from their kit when its version is higher: owned files, sections, and json values follow the three-state rules, so a user modification is kept when the kit content is unchanged and reported as a conflict when it differs. An equal version with changed content warns without an update, a lower version is shown as a downgrade, and reset to kit replaces owned content on explicit request.
- Installed items are removed on request: unchanged owned files are deleted and user-modified ones are kept and reported, owned sections go with their markers or stay without them, json values go when their item is the last owner, directories and shared files penates created are cleaned up while the removal leaves them empty, and orphans — installed items no kit provides anymore — stay listed and removable.
- After an interruption, penates reconciles the lock with the target before planning: staged temp files an interrupted apply left behind are removed, an installed item whose recorded content the target holds in another form is shown as modified and kept, and one whose recorded content the target lost is shown as broken and is installed again when applied.
- The item list follows the RFC 10.2 shape: rows are grouped under their kit's header, every status — selected, installed, update, downgrade, modified, broken, warning, conflict, orphan, kit unavailable — renders its own bracket marker, `/` filters by id, tags, and description, and `i` opens the item's details: description, contributions, changelog when the kit carries one, source kit, and the variable answers recorded at installation. The items of a kit that no longer loads appear as kit unavailable under the kit's header, and installed items of a kit that is not registered are grouped as orphans under its name.
- Applying is confirmed through a summary first (RFC 10.2): it lists every change per item with the reason of each action, the removals marked with `d` together with the content they leave behind, the items kept unchanged with a warning when the kit content differs, and every excluded item with its reasons. Nothing is written until the summary is confirmed with enter; esc returns to the list with the selection intact. The variable form interrupts before anything is written, and a required variable answered with an empty string shows the item excluded on the summary instead of asking again.

### Changed
- Adding a kit went from a bare path input to the full flow: the input completes directory names (tab, with the dropdown of the candidates), the kit previews live in the details pane a short interval after the last keystroke — on narrower terminals as a details view after enter — a kit proposing another target than the current one asks between registering that target and attaching there, attaching to the current target anyway, and cancel, and a first target is registered through an input prefilled with the kit's `target_hint` under an existence line. The preview's errors — a kit.yaml that does not read, with its position, a name already registered with its path, an attachment that already exists — show in the preview and keep the input editable; item-level problems list under the preview and do not stop the attach — the attached kit shows unreadable until its broken items are fixed.
- Variable forms ask at selection time instead of apply time: selecting an item with variables — or an update that introduces a new one — turns the details pane (wide terminals) or the details view into a form prefilled with the stored answers; `tab` moves between the fields, `enter` is accepted only when every required field holds a value, and `esc` clears the selection. The answers are saved into the pending actions like the other toggles and reach the lock on apply; nothing asks for variables at apply time anymore — a selection whose required answers went missing plans as excluded with its reason on the summary.
- The main screen is rebuilt on the new interface: kits and items form one tree under their kit rows — status glyphs with colors and ASCII fallbacks replace the bracket markers, pending marks sit at the right edge, the details of the row follow the cursor in a pane on wide terminals and open as a scrolling view on enter, `/` filters with match counts on the kit rows, and the footer names the keys of the row under the cursor. The first run explains kits and attaches a kit path at its `target_hint`; a major update opens its details for review before the space selects it; startup opens the last active target; the header shows the target and the pending count, the screen states the minimum terminal size. The old screens are removed; the apply summary, the results, and the apply-time variable forms carry over.
- Pending removals and resets of installed items whose kit is not registered — orphans of a kit that is gone entirely — are kept in the state now: a removal is planned from the lock alone and survives restarts, only the selection of such items is dropped with its answers.
- The state file becomes a registry: kits with their directories, targets with an optional display name, the attachments between them, the last active target, and per-target pending actions — the selected, reset, and removed items, the deferred detach and forget operations waiting for their apply, and the variable answers given at selection. The state saves on every mutation, and entries that no longer hold are dropped at load with a report. The old `state.json` format is not migrated: loading it fails with an error naming the file to delete.
- The product specification lives in `docs/concept.md`, a living document, instead of `docs/rfc-penates.md`: the concept absorbs the model and the rules of ownership, updates, and removal, states the three deviations the shipped build made as the actual behaviour, and drops the alternatives survey. The RFC is archived under `docs/archive/` with its status stamped, and code comments state their rules directly instead of citing RFC section numbers.
- The README introduces the tool to a new reader — the problem it solves, the main screen, a minimal kit, and the ownership rules — instead of a summary paragraph with links to the design documents.
- Updating an item no longer releases ownership of the json values its new version stops declaring: owned files, blocks, and json locations stay recorded exactly as installed until the item is removed, so a removal still cleans up everything penates wrote and a later version that declares the location again evaluates the user's content against the installation base.
- The penates data directory is `~/.config/penates` on every OS, honoring `XDG_CONFIG_HOME` when it is set and non-empty, instead of the platform configuration directory (`%AppData%` on Windows, `~/Library/Application Support` on macOS). Existing state is not migrated.

### Fixed
- Removing several items that own blocks or values in one shared file no longer overwrites each other's removal: the items compose their shared files across the run, so a later item's action rewrites what the earlier removals leave, and a shared file penates created is deleted when the run's removals empty it.
- An update that keeps a user-modified file or block no longer drops it from the lock record: content a plan leaves standing stays recorded with its installation base, so later updates and removals still see it.
- Removing an item no longer passes silently over the json content the user reshaped: an array element the user replaced or removed, and a value standing where the item installed another one, stay in the target and are named in the removal report like a modified value is.
- Applying into a target directory that does not exist yet no longer fails when an item writes a file directly into the target root.
