## [Unreleased]

### Added
- Initial release of penates: a terminal UI that installs configuration kits into harness configuration directories and records every file, section, and JSON value it writes in a per-target lock — updates and removals always see what penates owns, and what it did not write it never touches.
- Kits and targets live in a state registry under `~/.config/penates`, honoring `XDG_CONFIG_HOME` when it is set and non-empty: kits with their directories, targets with an optional display name, the attachments between them, the last active target, and the pending actions of each target — the selected, reset, and removed items, the variable answers given at selection, and the deferred detach and forget operations waiting for their apply — saved on every mutation, with entries that no longer hold dropped at load with a report.
- The main screen shows kits and items as one tree under their kit rows: every state — selected, installed, update, downgrade, modified, broken, warning, conflict, orphan, kit unavailable — renders its own glyph with a color and an ASCII fallback, pending actions take a separate mark at the right edge, the details of the row under the cursor follow in a pane on wide terminals or open as a scrolling view on `enter`, `/` filters by id, tags, and description with match counts on the kit rows, and the footer names the keys of the row under the cursor; the header shows the target and the pending count, the first run explains kits and attaches the first kit path at its `target_hint`, startup opens the last active target, a major update opens its details for review before the space selects it, and the screen states the minimum terminal size it needs.
- The details of an item cover its description, its contributions, the changelog the kit carries for it, its source kit, and the variable answers recorded at installation; the items of a kit that no longer loads appear as kit unavailable under the kit's header, and installed items of a kit that is not registered group as orphans under its name.
- Selected items install their file contributions from the kit into the target, section contributions append marked blocks to shared files — creating a file that is absent and leaving the rest of it untouched — and the per-target lock records every file and block penates writes.
- Items with json contributions install their values into shared JSON and JSONC files: each value lands by its RFC 6901 location, comments and formatting of untouched parts survive, an equal value owned by another installed item makes the item a co-owner, and the lock records every owned location with the hash of its value.
- Items with variables ask for the missing required ones in a form when the item is selected: the details pane or view turns into the form prefilled with the stored answers, `tab` moves between the fields, `enter` is accepted only when every required field holds a value, and `esc` clears the selection; the answers are stored in the lock and reused on the next run, templated contributions get `{{var}}` substituted, and an unknown placeholder or a required variable without a value excludes the item with its reason on the apply summary.
- Installed items are updated from their kit when its version is higher: owned files, sections, and json values follow the three-state rules — a user modification is kept when the kit content is unchanged and reported as a conflict when it differs — and content a plan leaves standing stays recorded with its installation base, so later updates and removals still see it; ownership of a location survives a version that stops declaring it, an equal version with changed content warns without an update, a lower version is shown as a downgrade, reset to kit replaces owned content on explicit request, and a bump across a major version is marked for review in the error style next to the version arrow.
- Installed items are removed on request: unchanged owned files are deleted and user-modified ones kept and reported, owned sections go with their markers or stay without them when the user reshaped the file, json values go when their item is the last owner — an array element the user replaced or removed stays and is named in the report — and directories and shared files penates created are cleaned up while the removal leaves them empty, with several removals in one shared file composing instead of overwriting each other; orphans — installed items no kit provides anymore — stay listed and removable, and a pending removal of an orphan is planned from the lock alone and survives restarts.
- After an interruption, penates reconciles the lock with the target before planning: staged temp files an interrupted apply left behind are removed, an installed item whose recorded content the target holds in another form is shown as modified and kept, and one whose recorded content the target lost is shown as broken and is installed again when applied.
- Applying is confirmed through a summary that groups the pending items by verb — install, update, remove, reset — with a mark per path (`+` a file, block, or value is created, `~` owned content is replaced, `-` owned content is deleted, `=` owned content is kept without a write, `!` content is kept and released from the lock), names the content the removals leave behind, lists every excluded item with its reasons, and reads "nothing to apply" — enter staying unavailable — while every pending item is excluded; nothing is written until the summary is confirmed, and confirming runs the apply item by item with a progress view that shows the spinner of the item being applied and a check or a cross on the finished ones and cannot be left; the results name every applied item with its verb and version, the content a removal kept, and every failed or excluded item with its reason.
- On exit penates prints the changes applied during the session to the regular output, so a record remains in the terminal history: one block per target, the installed and updated items with the versions they moved between, the removed ones with the files their removal kept in parentheses — and nothing at all when nothing was applied.
- A kit is registered through a path input with directory completion — tab, with the dropdown of the candidates — and a live preview of the kit the path holds, in the details pane or as a details view on narrower terminals: a kit proposing another target than the current one asks between registering that target and attaching there, attaching to the current target anyway, and cancel, and a first target is registered through an input prefilled with the kit's `target_hint` under an existence line; preview errors — a kit.yaml that does not read, with its position, a name already registered with its path, an attachment that already exists — show in the preview and keep the input editable, while item-level problems list under the preview and do not stop the attach: the attached kit shows unreadable until its broken items are fixed.
- `e` on a kit row points the kit to a new directory through the path input with directory completion: the pane previews the kit the new directory holds, a kit of another name is a rejection — "Add it as a new kit instead" — and an unreadable kit's pane states its read error and the installed items it keeps frozen until the kit points somewhere readable.
- `d` on a kit row detaches the kit from the target: a kit without installed items detaches at once with a notice, one with installed items opens a dialog — remove its items from the target first, and the kit detaches when the apply that removes them completes, its row showing "detaching" until then, or keep them installed as orphans; a deferred detach completes only when its apply removed everything it covers and is dropped, with a shown reason, otherwise, and the apply's results report both.
- `R` rescans the registered kits and reports what its diff brought — the new items, the updates, and the orphans — together with the pending actions it invalidated, counting both in one message.
- `t` opens the target list under the header: fuzzy search over the display name and the path, the current target marked beside the counts of its kits and installed items, `+ add target` with directory completion and the existence line, and `ctrl+r` renaming the display name the header shows; `enter` switches targets — the pending actions of each target stay saved with it, switching never asks and never discards, and a target that holds saved pending actions offers them for restoration on entering, reporting the invalid ones the restore dropped; `ctrl+d` removes a target through a dialog: either its installed items are removed through the summary and the target is forgotten when that apply completes, or the target is forgotten at once — its lock deleted, its files untouched and no longer owned.
- `ctrl+p` opens a command palette over the fixed command set — Add kit, Detach kit, Edit kit path, Switch target, Add target, Rename target, Remove target, Rescan kits, Apply, Clear pending actions, Help, Quit — with fuzzy search, a command acting on a kit taking the kit under the cursor and asking for one outside it, and a direct key shown at the right of its row; Clear pending actions drops the saved item actions and reports how many went; `?` opens the full help — the keys grouped by context, global, kit row, item row, `+ add kit` row, and the status and pending glyph legends, scrolled and closed by `esc`.
- Quitting with pending item actions opens a Quit/Back dialog first — the default is Quit, `esc` goes back — and without them `q` quits at once; `ctrl+c` quits only from the second press, the first arms the quit with a notice and any other key disarms it, and the second quits immediately without dialogs, during the apply too; notices carry their full texts, and attaching a kit or detaching one without installed items offers `u` undo while the notice lives — one press performs the reverse operation, any other key or the age-out drops the offer.
- The command line takes commands, not positional arguments: `penates version` prints the version and the commit the binary was built from — `penates dev (unknown)` on a plain `go build`; `penates licenses` prints the components included in the binary — penates, the Go standard library and runtime, and the third-party modules — with the license text of each, the third-party texts embedded in the release builds while a plain build carries only the first two and points at the releases page; a first argument that names no command is rejected with one `Error:` line that names what to run.
